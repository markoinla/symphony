Symphony — linear-agent + sandbox-sdk Architecture

Cloudflare-native Linear agent. A Hono Worker terminates Linear webhooks, drives long runs through a Cloudflare Workflow, and HMAC-signs the sibling sandbox-dispatcher Worker — which runs pi/claude/codex inside Cloudflare Sandbox containers built on the @cloudflare/sandbox SDK.

Topology

Linear delivers webhooks to the linear-agent Worker. The Worker drives a Cloudflare Workflow (SessionRunner) that streams agent runs from the sandbox-dispatcher Worker over HMAC-signed SSE. Sandboxes run on the @cloudflare/sandbox SDK (covered by the .claude/skills/sandbox-sdk/ skill).

SessionRunner Workflow src/workflows/session-runner.ts

One Cloudflare Workflow class with two run modes: agent_session (Linear-visible) and trigger (headless). Instance id is set to the Linear agentSession.id so Linear retries collide on an existing instance idempotently. Every step is checkpointed; eviction resumes from the last completed step. The outer try/finally always calls stopSandboxQuiet() so an errored run can't leave a zombie sandbox burning CPU.

agent_session mode — steps

  1. load-token — read install access_token + GitHub install id from D1. refreshInstallTokenIfNeeded rotates it if expires_at is inside the run window.
  2. post-initial-thought — meet Linear's 10s SLA. Picks workflow name from workflow_overrides.name if present.
  3. start-session-side-effects (only on action=created) — set issue delegate to the agent viewer, attach externalUrls to /dashboard/sessions/<id>, post initial 2-item plan. All best-effort — never throws.
  4. resolve-inputs — ProjectStore.getByTeamId → repo; resolvePrompt → promptContext|comment|description; resolve engine/model/max_turns via the chain below; append Linear GraphQL skill marker via withLinearGraphqlReference.
  5. mint-github-token — JWT-mint per-installation token if GitHub App is configured, else fall back to env.GITHUB_TOKEN.
  6. record-session-start — insert agent_sessions row with config_snapshot.
  7. turn-N loop (up to max_turns) — for each turn:
    • resolve-linear-mcp-token-N: per-user Linear OAuth from accounts (preferred) → install access_token fallback; delivered to sandbox as LINEAR_API_TOKEN.
    • turn-N with timeout: 35 minutes (Workflows step default is 10m; dispatcher caps runs at 30m so we need headroom): dispatcher.runStream() yields NormalizedEvents; each event is persisted to agent_session_events and (in agent_session mode) mapped to a Linear activity posted live.
    • On turn_end:needs_continuation, build continuation prompt and loop. On result, exit.
  8. step.waitForEvent('linear.prompted', 25m) — bounded wait for follow-up prompted webhook between turn batches (Linear marks sessions stale after ~30m). The webhook route forwards via instance.sendEvent when the runner is alive, or spins up a :rN-suffixed fresh instance otherwise.
  9. post-terminal-activity — postResponse on success, postError on failure (engine exit ≠ 0 or in-band error).
  10. update-final-plan (only on action=created) — completes/cancels the 2-item plan.
  11. record-session-end — flips agent_sessions row to completed / error with completed_at.
  12. stop-sandbox (outer finally) — DispatcherClient.stop(issueId). Idempotent.

trigger mode

Mirrors agent_session mode minus Linear-side activity posts. Today unused at the call site — trigger flows queue the agent_session mode with a synthesized webhook via dispatch-trigger.ts, which gives the same Linear-visible timeline. Kept on the type for future headless workflows (cron-fired runs).

Engine / model / max_turns resolution

Every dispatch resolves three runtime fields through the same precedence chain. Higher entries win. projects.{engine,model,max_turns} columns are not consulted — they remain to avoid a destructive migration but the runner ignores them.

RankSourceApplies toNote
1workflow_overridesTrigger-fired runsSnapshot of workflow row at queue time (engine/model/max_turns + allowed/disallowed_tools/permission_mode). Frozen — mid-run workflow edits don't perturb in-flight. NULL workflow.model means "inherit" so the field is omitted.

Request flows

1. Linear @-mention → PR

  1. User @-mentions the agent in Linear → Linear POSTs AgentSessionEvent.created to /webhook.
  2. Webhook route verifies HMAC, dedupes on (webhookId, sessionId) in LINEAR_TOKENS KV, inserts webhook_events row.
  3. SESSION_RUNNER.create({id: agentSession.id, params:{mode:'agent_session', event}}) — Workflow instance keyed on session id (idempotent on retry).
  4. Workflow steps: load-token → post-initial-thought → start-session-side-effects (delegate + externalUrls + plan) → resolve-inputs → mint-github-token → record-session-start.
  5. Turn loop: dispatcher.runStream() over HMAC-signed SSE; each event is persisted to agent_session_events and (live) posted as a Linear activity via mapToActivity.
  6. step.waitForEvent('linear.prompted', 25m) — picks up follow-ups; webhook route forwards them via instance.sendEvent.
  7. post-terminal-activity (response or error) → update-final-plan → record-session-end. Outer finally: dispatcher.stop(issueId).

2. Trigger-initiated workflow (state change / label add)

  1. Linear Issue webhook → /webhook.
  2. event-mapper-inbound emits normalized EventTuple[] (state_entered uses data.state.name, label_added per added label).
  3. ensureDefaultWorkflow(orgId) — idempotent first-delivery seed.
  4. For each tuple: resolveWorkflow picks the best (workflow, trigger) by scope tier (user>team>org) then priority.
  5. dispatchTrigger: resolve project → render Liquid prompt → refresh install token → createAgentSessionOnIssue → linearSessionId.
  6. Build synthetic AgentSessionEvent(action:created) with promptContext = rendered prompt.
  7. SESSION_RUNNER.create with mode agent_session + workflow_overrides snapshot (engine/model/max_turns/name/+policy).
  8. Same Workflow as @-mention runs — Linear timeline renders it identically.

3. Stop signal

  1. Linear prompted webhook arrives with agentActivity.signal: "stop".
  2. Webhook route detects via extractStopSignal (probes 3 paths).
  3. SESSION_RUNNER.get(sessionId).terminate() — Workflow finally is not trusted to run after terminate.
  4. DispatcherClient.stop(issueIdentifier) — destroys the per-issue sandbox DO.
  5. postResponse("Stopped at user request.") to Linear timeline (with refresh-on-401).
  6. AgentSessionStore.update(status:'stopped').

Anti-patterns called out

  • Don't use internal clients (CommandClient, FileClient) — use sandbox.* methods.
  • Don't skip export { Sandbox } — Worker won't deploy.
  • Don't hardcode sandbox IDs for multi-user — key on user/session.
  • Don't forget destroy() for temporary sandboxes.

Key patterns & invariants

Webhook dedupe

60-min KV markers keyed per (webhookId, agentSessionId) or (webhookId, issueId, webhookTimestamp). Retries collapse; real re-transitions get distinct keys via webhookTimestamp.

Workflow id collision

SESSION_RUNNER instance id = Linear agentSession.id. Linear retries idempotently collide on the existing instance.

Single-flight OAuth refresh

Per-orgId refreshInstallToken is single-flight within a Worker instance — dozens of activity posts from a streaming turn collapse onto one refresh.

Envelope encryption

Random per-row DEK (AES-GCM-256) wrapped by master KEK (also AES-GCM-256, Workers secret). kek_version drives rotation; old KEK kept available during re-wrap migration.

HMAC wire compat

Pinned test vector "test-secret-do-not-use-in-prod" / "{\"scope\":\"alice\"}" → 1628b1de… asserted in dispatcher.test.ts, sandbox-dispatcher hmac.ts, and the Elixir DispatcherClient. Drift breaks all three suites loudly.

REST/MCP unification

MCP tool handlers dispatch synthetic Requests into the same v1 router REST callers use. Validation, scope enforcement, persistence, error envelopes match exactly — no parallel implementation to drift.

Stop-signal path

Handled fully in the webhook route — Cloudflare Workflow's finally doesn't run reliably after terminate(). Order: terminate instance → dispatcher.stop → postResponse → DB status='stopped'.

Per-issue sandbox branch

Branch derived as symphony/<lowercased-sanitized-identifier> — gives continuity across multiple runs on the same issue (e.g. SYM-123 → symphony/sym-123).

Step timeout headroom

Workflow turn steps use timeout: "35 minutes". Cloudflare's default 10m races dispatcher's own 10m default and surfaces as WorkflowTimeoutError; dispatcher caps runs at 30m so 35m gives SSE-close + post-terminal-activity room.

Linear skill marker

Every dispatched prompt is post-processed by withLinearGraphqlReference to append a marker block with issue/team UUIDs. The baked-in linear skill in the sandbox baseline reads LINEAR_API_TOKEN env and calls api.linear.app/graphql directly — no hosted MCP dependency.
